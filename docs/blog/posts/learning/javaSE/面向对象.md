面向对象最有用的地方，是把“会一起变化的状态与行为”放在一起，再用明确的边界连接它们。类的数量多，并不代表设计更好；一个对象能清楚说明自己的职责，才是好的开始。

## 封装：让状态始终有效

把字段设为 `private` 只是第一步。更关键的是，让对象只暴露有业务含义的操作，避免外部代码随意把它改成无效状态。

例如账户与其开放 `setBalance`，不如提供带校验的 `deposit` 和 `withdraw`；订单与其开放任意 `setStatus`，不如提供“确认”“取消”等受规则约束的操作。

对于集合字段，还要考虑是否暴露内部可变集合。可以返回只读视图，或根据需求返回快照，例如 Java 10 起可用的 `List.copyOf(items)`。它是不可修改的浅拷贝，不会让元素对象本身也变得不可变。

## 接口：描述调用方真正需要的能力

假设业务需要发送通知。业务关心的是“把消息发出去”，不应直接依赖某个邮件厂商的客户端。

```java
interface MessageSender {
    void send(String recipient, String message);
}
```

这个接口的价值在于形成稳定的调用边界。以后增加短信或替换供应商，业务流程不必跟着修改。接口也不宜把所有厂商功能都塞进去，否则调用方仍会被不需要的能力牵动。

## 多态与组合：把变化交给被依赖的对象

下面的代码使用 Java 17，可以保存为 `NotificationDemo.java` 后执行 `java NotificationDemo.java`。

```java
import java.util.Objects;

public class NotificationDemo {
    interface MessageSender {
        void send(String recipient, String message);
    }

    static final class ConsoleSender implements MessageSender {
        public void send(String recipient, String message) {
            System.out.println(recipient + " <- " + message);
        }
    }

    static final class NotificationService {
        private final MessageSender sender;

        NotificationService(MessageSender sender) {
            this.sender = Objects.requireNonNull(sender);
        }

        void welcome(String recipient) {
            if (recipient == null || recipient.isBlank()) {
                throw new IllegalArgumentException("接收人不能为空");
            }
            sender.send(recipient, "欢迎来到这里");
        }
    }

    public static void main(String[] args) {
        MessageSender sender = new ConsoleSender();
        NotificationService service = new NotificationService(sender);
        service.welcome("reader");

        // 测试替身：观察服务发出了什么，不需要连接邮件服务器。
        MessageSender testSender = (to, message) ->
            System.out.println("[test] " + to + ": " + message);
        new NotificationService(testSender).welcome("test-reader");
    }
}
```

`NotificationService` 通过构造器接收依赖，这就是依赖注入的一种形式，完全不需要框架才能使用。服务组合一个发送器；运行时实际调用哪个 `send` 实现，由传入的对象决定。

## 继承适合什么，组合又适合什么

继承表达“它是一种什么”，组合表达“它需要谁来完成什么”。并不是所有复用都需要继承。

| 设计问题 | 可以先考虑的方式 |
| --- | --- |
| 几种对象有统一的调用约定 | 接口 |
| 一个流程需要替换其中一步 | 组合一个策略对象 |
| 确实存在稳定的子类型关系 | 继承，并检查子类是否能替换父类 |
| 只想共享几行工具代码 | 普通方法或独立工具类，避免为复用制造层级 |

如果某个子类必须把父类的正常操作改为“抛出不支持异常”，需要重新检查这个继承关系。调用方对父类型的合理预期，可能已经被破坏。

## equals 与 hashCode：对象如何参与集合

对象放进 `HashSet` 或作为 `HashMap` 的键时，相等性规则会参与查找。覆盖 `equals` 后，也要按同一组关键字段覆盖 `hashCode`。

两个对象如果 `equals` 为 `true`，它们的 `hashCode` 必须相同；哈希值相同却不保证对象相等。参与相等性计算的键字段最好保持稳定，否则对象加入哈希集合后再修改字段，可能导致查找失败。

Java 的 `record` 能为数据载体生成基于组件的相等性方法，但它对引用组件提供的也是浅层不可变性。组件如果是可变列表，仍需考虑防御性复制。

## 把例子再向前推一步

可以尝试增加一个 `RecordingSender`，把接收人和内容保存到列表，然后验证：合法接收人发送一次，空接收人不发送。这样测试的是服务的对外行为，而不是它内部调用了几个私有方法。

再想一想：如果需求变成“发送失败后重试”，重试属于欢迎文案的职责，还是发送器的能力？沿着这个问题，可以继续学习装饰器与职责分离。
